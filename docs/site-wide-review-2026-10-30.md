## 🚨 一、緊急：資安

### S1. 資料庫對外完全公開（已實測）
- GitHub repo 是**公開**的，裡面有 Supabase 網址與公開金鑰（這把金鑰本來就會出現在網頁裡，問題不在金鑰本身）。
- 真正的問題是資料表**沒有開 RLS（資料列權限）**（Gemini 文件中也有「關閉 RLS」的 SQL）。實測**不用登入**就能讀到：

  | 資料表 | 筆數 | 外洩欄位 |
  |---|---|---|
  | `guild_members` | 241 | 角色名、聯繫方式、備註、曾用名… |
  | `profiles` | 11 | **email**、角色、到期日、可查看／編輯的幫會 |
  | `guild_rosters` | 15 | 全部排表 |
  | `guilds`、`preparation_roles`、`preparation_skills` | 3 / 57 / 42 | 全部 |

- 寫入權限我**沒有測試**（避免改到你的資料），但在 RLS 關閉的情況下，寫入通常也同樣開放，代表任何人都可能**修改或刪光**所有幫會資料。

**修改建議**：所有資料表開啟 RLS，並依下表加上規則（先寫成 SQL 在 Supabase 測試，確認網站正常再逐表啟用；出問題可用 `alter table … disable row level security` 立即還原）：

| 資料表 | 讀取 | 新增／修改／刪除 |
|---|---|---|
| `guilds` | 有該幫會查看權 | 總管理員 |
| `guild_members`、`guild_rosters` | 有該幫會查看權 | 有該幫會**編輯**權 |
| `preparation_roles`、`preparation_skills` | 有該幫會查看權（通用技能所有人可讀） | 有該幫會編輯權（通用技能限總管理員） |
| `profiles` | 自己那一筆；總管理員全部 | 見 S2 |

做法：在資料庫建立 `can_view_guild(guild_id)`、`can_edit_guild(guild_id)`、`is_super_admin()` 三個函式，每張表的規則都呼叫它們，之後新增資料表也沿用。

### S2. 任何人都能把自己升成總管理員
- 註冊是開放的（登入頁可自行註冊 7 天試用）。註冊後在瀏覽器主控台執行一行 `supabase.from('profiles').update({ role: 'super_admin', expire_at: '2099-12-31' })`，就能變成總管理員並取得所有幫會權限。目前前端的權限判斷都只是「隱藏按鈕」，擋不住。
- **修改建議**：`profiles` 的修改限制為：一般使用者只能改自己的 `username`；`role`、`expire_at`、`status`、各種 `guild_ids` 只有總管理員能改。可用資料庫 trigger 檢查「非總管理員時這些欄位不得變動」。

### S3. 停權、到期、刪除帳號實際上都沒有作用
| 功能 | 現況 | 位置 |
|---|---|---|
| 停權 | 只寫入 `status = '已停權'`，**全站沒有任何地方檢查它**，被停權的人照常使用 | `AdminDashboard.vue` |
| 試用到期 | 只在「按登入按鈕」時檢查；瀏覽器保留登入狀態的人重新整理就直接進站，不會被擋 | `App.vue` `checkSession` |
| 刪除帳號 | 只刪 `profiles` 那一筆，登入帳號還在；對方再登入時，`LoginView.vue` 會**自動重建資料並送 7 天試用** | `AdminDashboard.vue`、`LoginView.vue:132` |

**修改建議**：
1. 把「未停權且未到期」寫進 S1 的權限函式，資料庫層直接拒絕，前端繞不過。
2. `App.vue` 的 `checkSession` 也檢查一次，給使用者明確的「已停權／已到期」提示並登出。
3. 刪除帳號改用 Supabase Edge Function（伺服器端用管理金鑰刪除登入帳號），或改為「停權」取代刪除。

### S4. 舊後端資料夾與明文密碼在公開 repo
- `server/`（Express 舊後端）網站已不使用，但 `server/users.json` 內有一組**明文密碼**，`server.js` 也以明文比對密碼，且公開在 GitHub。
- **修改建議**：刪除整個 `server/` 資料夾；若該密碼在其他地方用過，請一併更換（刪檔後 Git 歷史仍查得到，所以換密碼比刪檔重要）。

## 🔴 二、高：資料正確性

### D1. 截圖導入裡寫死了測試名單
`Members.vue:1131-1149`：辨識出的文字只要包含「璃玥、曉玖、琉璃、嗨小之、浮雲、一劍星河」或幾組數字，就**不使用辨識結果**，直接回傳固定的 4～6 人假名單。真實截圖剛好有這些名字時，會導入錯誤的人。
**建議**：刪除這兩段測試用判斷。

### D2. 批量操作會動到畫面上看不到的成員
勾選成員後切換幫會、改搜尋字或流派篩選，**勾選不會清除**。此時按「批量刪除／移動／修改」，會處理到另一個幫會或已被篩掉的人，而畫面上只顯示「(N)」人數。
**建議**：切換幫會、搜尋、篩選時清空勾選；或批量操作只處理「目前畫面上看得到且有勾選」的成員。

### D3. 帳號 ID 規則會讓部分人無法註冊或撞號
`LoginView.vue` 把帳號 ID 轉成 `ID@app.com` 時，會**刪掉英數與底線以外的所有字元**：
- 中文 ID → 變成 `@app.com`，註冊直接失敗，訊息看不懂。
- `Abc.1`、`abc-1`、`ABC1` 會變成同一個帳號，第二個人註冊時被告知「已被註冊」。

**建議**：輸入時就檢查並提示「帳號只能使用英文、數字、底線」，不要默默刪字。

### D4. 戰備頁只能管理「第一個」幫會的職能與技能
`RoleManagement.vue`、`SkillManagement.vue` 固定取 `profile.guild_id` 或授權清單第一個幫會；總管理員若沒指派幫會，則取資料表的第一筆。戰備頁**沒有幫會切換**，其他幫會的職能永遠改不到，但成員頁卻是依「目前選的幫會」讀職能，兩邊對不上。
**建議**：戰備頁左上加幫會切換（與成員頁相同），並記住上次選擇。

## 🟠 三、中：效能與功能

### M1. 聯賽列表一次下載所有排表內容（多 146 倍）
`League.vue:415` 用 `select('*')` 撈全部聯賽，連同每場完整的 `matrix_teams`。實測：

| 撈法 | 大小 |
|---|---|
| 現在（全部欄位，15 場） | **689 KB** |
| 列表實際需要的欄位 | 4.7 KB |

每多一場聯賽就再多約 45 KB，手機網路下會越來越慢。
**建議**：列表只選需要的欄位並以 `guild_id` 篩選；`matrix_teams` 在打開排表時才載入（`RosterBoard` 本來就會自己再讀一次）。

### M2. 成員頁下載所有幫會的成員
`Members.vue` 撈整張 `guild_members`（241 人、101 KB）再在前端以「幫會名稱」過濾，其他幫會的聯繫方式也一起下載到瀏覽器。
**建議**：查詢加 `.in('guild_id', 可查看的幫會)`，比對改用幫會 id 而非名稱。

### M3. 批量操作逐筆送出
導入、批量修改、移動、刪除都是一人一個請求（76 人＝76 次）。中途斷線只會留下一半結果。
**建議**：改為一次送出（`insert([...全部])`、`.in('id', ids)`），速度快且要嘛全成功要嘛全失敗。

### M4. 大部分寫入沒有檢查錯誤
supabase-js 失敗時不會丟出例外，但多數地方只 `await` 不看 `error`（例如新增／刪除成員、快速切換流派與狀態、改幫會名稱、刪除幫會、改角色權限）。畫面先改了、資料庫其實沒寫入，使用者完全不知道。開啟 RLS（S1）後若規則沒設好，這類「默默失敗」會更多。
**建議**：建立共用的 `runQuery()` 包裝：失敗時跳提示並還原畫面。

### M5. 任何登入者都能新增幫會、看到幫會設定
- 「+ 新增幫會」對所有人顯示（含試用帳號），新增後自動給自己編輯權。
- 每個幫會旁的齒輪（改名、**刪除幫會**）不檢查編輯權限。
- 刪除幫會沒有檢查錯誤，也沒有處理該幫會的成員與排表。

**建議**：新增幫會限總管理員（或改為「申請」）；齒輪只對有編輯權者顯示；刪除幫會前提示會一併影響多少成員與聯賽。

### M6. 從 CDN 載入的套件有已知漏洞或未鎖版本
| 套件 | 問題 | 建議 |
|---|---|---|
| `xlsx` 0.18.5（cdnjs） | 有已知安全漏洞（原型污染、ReDoS），且被用來讀使用者上傳的檔案 | 改用 SheetJS 官方最新版（0.20.x），以 npm 安裝 |
| `tesseract.js@5`（jsdelivr） | 只鎖大版本，CDN 更新時行為可能突然改變 | 鎖定完整版本，或以 npm 安裝 |
| `html2canvas`（cdnjs） | `package.json` 已安裝卻仍從 CDN 載入，CDN 被擋時導出失敗 | 直接 `import` |

### M7. 總管理員控制台改角色沒有確認
角色下拉選單一改就立即寫入，沒有確認也沒有檢查錯誤；誤點可能把別人升成總管理員，或把自己降級後失去控制台。
**建議**：改角色前確認；禁止把自己降級；失敗時還原選單。

### M8. 兩條頂部列、「帳號名稱」容易誤會
- `App.vue` 的深色帳號列與各頁 `Navbar` 都有帳號名稱與登出按鈕，重複。
- 「個人資料」可改「帳號名稱」，但只改顯示名稱，**登入仍要用原本的 ID**，使用者改完可能以為要用新名稱登入。

**建議**：合併成一條頂部列；欄位改名為「顯示名稱」並註明「登入帳號不變」。
